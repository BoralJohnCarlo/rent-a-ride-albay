Browser notifications
=====================

Install server dependencies with `npm ci` in `server`, then configure these server environment variables:

```
VAPID_PUBLIC_KEY=<public key>
VAPID_PRIVATE_KEY=<private key>
VAPID_SUBJECT=mailto:<real support email address>
```

Generate a key pair once with `npx web-push generate-vapid-keys` from the server directory. Keep the private key in your hosting provider's secret settings, outside source control. Keep the pair stable across restarts and instances. No client environment variables are needed. Restart the server after configuration.

Availability now validates key encoding, the P-256 public/private key pairing, the contact URI, and VAPID signing using the provider library. Missing, malformed or mismatched configuration returns unavailable with no public key exposed; it does not enable subscriptions or process jobs. Validation is cached until configuration values change and never logs private keys. This is local validation, not a live delivery test.

The feature remains unavailable until all three variables exist. It preserves existing in-app and email notifications and adds a customer pickup reminder. It requires MongoDB index creation (including Notification's partial unique recipient/dedupeKey and pushPending/createdAt indexes, PushSubscription's unique endpoint/expiry indexes, and PushDelivery's unique notification/subscription and expiry indexes), HTTPS in production, and outbound HTTPS access to browser push services. If automatic index creation is disabled, create these declared indexes before starting the new code; no index drops are required. Serve `client/public/push-sw.js` as `/push-sw.js` with JavaScript content type; do not rewrite it to the SPA HTML page or cache it immutably.

All three roles can enable alerts from their Notifications page. Customers and operators can also use Settings > Browser Notifications. Permission is requested only after clicking Enable. On iOS/iPadOS, Web Push requires a supported Home Screen web app. Unsupported browsers keep the in-app bell.

Settings reads have a 12-second overall deadline. Enable has a 30-second deadline, including the browser permission prompt and worker readiness. HTTP requests use an 8-second timeout and an abort signal. When a deadline expires, later workflow steps are prevented even if a native browser promise resolves late. Native browser operations already started cannot be forcibly cancelled. Failed-save rollback is bounded to two seconds.

Disable performs browser unsubscribe and server revocation independently, with four- and eight-second deadlines after bounded browser discovery. The UI reports confirmed local-only or server-only success instead of waiting on a fresh server read. If both fail, it reports that disabling could not be confirmed. The load-error view offers a local-disable action so a failed settings read does not prevent an unsubscribe attempt. No other application API timeouts are changed.

Subscription mutations in settings, failed-save rollback and logout share a coordinator. A timed-out native browser call retains the coordinator until the underlying call actually settles. A later Enable waits for it and re-reads the subscription under the coordinator before saving. If the browser operation remains stuck, Enable returns its bounded timeout without saving a subscription that an older cleanup could still remove. Expired waiting actions never run later. Web Locks coordinate tabs when supported; other browsers receive coordination within the current page. Permission prompts are still requested directly from the user's click, before waiting for the coordinator.

Subscriptions belong to the current login session and expire with its token. Logout clears the cookie regardless of cleanup failure; the client also attempts to unsubscribe locally and close desktop notifications. Server cleanup is bounded to two seconds. If both the server database and browser cleanup are unavailable, subscription revocation cannot be guaranteed until token expiry or later cleanup. Password changes and suspension prevent future sends. After signing in again, enable browser notifications again. Enabling another account on the same browser transfers that browser subscription to that account. Queued jobs retain their original account/session binding and cannot follow that transfer.

Only allowlisted events in `utils/pushPolicy.js` generate pushes. Existing scheduled reminders retain their existing deduplication. An hourly pickup sweep reminds customers within 24 hours before the project's pickup reference time. The unique recipient/dedupeKey index prevents concurrent instances from creating the same pickup reminder. Each notification ID is the desktop notification tag, replacing duplicate cards across tabs or retry attempts. New event types default to in-app only. Support currently has no urgency field, so ordinary support conversations are not pushed.

Deleting a keyed reminder or clearing the inbox retains a dismissed deduplication receipt, clears its message/title and entity metadata, marks it read, and cancels pending push recovery. It is excluded from notification lists, searches, counts and direct mark-read access. Other notifications are physically deleted as before. Receipt keys include the booking and pickup time, so a rescheduled pickup can receive a new reminder.

New notifications save a pushPending flag in the same database write as their content. The minute worker recovers pending enqueue operations from the last hour, including crashes before queue creation and partial multi-device writes. It clears the flag only after all queue writes complete, or when an event is ineligible. Recovery is idempotent and does not reset completed job receipts. Subscriptions carry an enabledAt timestamp, so recovery does not replay old events to a newly opted-in or re-enabled session. Existing legacy notifications without the flag are not backfilled.

Recovery failures are isolated per notification, preserving the pending flag for another sweep while continuing healthy notifications. If the recovery scan itself fails, the worker still attempts existing delivery jobs. Browser receipt database opens and all read/write transactions have 1.5-second timeouts; timed-out transactions are aborted, connections closed, and subsequent pushes can proceed using stable tags as a fallback.

Push payloads deliberately contain no customer names, amounts, booking details or reference codes. Clicking opens a booking when its metadata supplies a safe customer booking ID, otherwise the relevant role's inbox. Delivery jobs are persisted before contacting the provider. Temporary network errors, 408/425/429 and 5xx responses retry up to five attempts with exponential backoff and provider Retry-After support, within one hour of notification creation. The cron worker runs every minute and also on server startup; atomic leases coordinate instances and recover jobs after a crashed worker. Completed receipts prevent re-enqueueing duplicates until expiry. Provider 404/410 responses remove invalid subscriptions; other permanent errors stop retries. Every attempt rechecks account/session ownership, token expiry, suspension, credential version, event policy, and whether the notification still exists and is unread. If a worker crashes after the provider accepts a message but before the receipt is saved, it may send again. The service worker serializes incoming pushes and saves displayed notification IDs in IndexedDB until their delivery window expires, suppressing repeats even after dismissal or a worker restart. Expired browser receipts are pruned on subsequent writes. If browser storage is blocked or unavailable, it falls back to stable tags without renotification. Exactly-once delivery cannot be guaranteed across the provider and browser: a crash between display and saving its browser receipt remains possible. Push is best effort, not guaranteed delivery. Browser/OS settings and battery policies can affect delivery.

Verification: run `node --test tests/notifications/*.test.js` in `server`, `node --test client/tests/browserPushRequests.test.mjs client/tests/browserPushWorker.test.mjs client/tests/pushCleanup.test.mjs` from the repository root, and `npm run build` in `client`. The integration tests use a uniquely named temporary test database on MONGO_URI, remove it afterward, and mock provider delivery. Run `node tools/verify-browser-notifications.mjs` for isolated Chrome UI checks of retry, all three roles, account switching, server cleanup failure during Disable, and logout API failure. That fixture uses fake browser push APIs and never signs in or sends real pushes. For live acceptance, use two accounts and a configured HTTPS deployment: opt in, create an important event, close the tab, receive/click the desktop alert, verify routine events stay in-app, disable, and verify logout/password change stop delivery. Also check permission denial and switching accounts on a shared browser.
